# 13 · 前后端接入时需要补充、调整、重构的点

> 用途：设计阶段先按前端合理的体验做，凡是与后端现状不一致的地方记在这里，供接入时讨论。
> 约定：**P0** 不解决会让设计主流程走不通；**P1** 影响体验但可降级；**P2** 想法记录，暂不展开。
> 字段级细节以 `packages/api-client/src/schema.d.ts` 为准，本表基于对 GEOEval 规格与 README 的阅读，接入时核对。

## 一、前端设计采用的、与后端一致的约定（直接按后端做）
| 主题 | 约定 |
|---|---|
| 评测问题 | 由系统生成，用户不可编辑；开始前有“准备中 → 就绪 / 请重试”一步 |
| 诊断次数 | 每个资料版本一次成功诊断；样本有效数 ≥ 17/20 才算成功；“请重试”不扣额度 |
| 进度 | 轮询 `platformProgress` 与阶段；SSE 只当“刷新提示”，不当数据来源 |
| 写操作 | 带 `revision` 或 `idempotencyKey`；金额、确认文章、开始诊断不做乐观更新 |
| 文章 | 草稿 / 已确认；编辑已确认文章会回到草稿；重新生成需“会替换现有内容”提示；失败显示后端 `failure.message` |
| 发布 | 随机 / 精准两种模式；有报价问题状态；必须勾选条款；结果逐条回传 |
| 订单 | 只有“延迟”标记，无取消和退款；结束后有 72 小时结算窗口，固定文案“已约定退回 ⚡X，待订单结束结算 / 已退回 ⚡X” |
| 充值 | 1 元 = 10 积分；目前只有支付宝 PC 可用；`CLOSED` 展示为“未支付”；以 verify 接口确认到账 |
| 品牌资料 | 诊断必填：行业（两级，“其他”需 2–60 字说明）、公司名、高德校验的地址、主营产品（2–80 字）、2–6 个品牌特点、联系人+手机；写文章加强项：价格、1–5 个目标客户、背景、定位、特点详情 |

## 二、需要后端补充（前端会按理想体验设计）

### 通知（站内，用户已确认）
| 前端需要的种类 | 后端现状 | 优先级 |
|---|---|---|
| 诊断完成 / 失败（需重试） | 已有 | — |
| 文章生成完成 / 失败 | 已有 | — |
| 订单延迟 | 无 | P1 |
| 订单完成（含结算退回） | 无 | P1 |
| 积分变动（充值到账、退回） | 无 | P1 |

- 点开某品牌的诊断通知，前端需先切换到该品牌；接口最好带 `brandId`。
- 通知偏好（开关）目前没有接口；设计上只放一个“诊断完成通知”开关（Running 页已有），其余不做。P2。

### 品牌
| 项 | 说明 | 优先级 |
|---|---|---|
| 归档 / 恢复 / 删除品牌 | 品牌切换器的“管理品牌”会需要；先不设计，记录需求 | P2 |
| 资料完整度 | 前端按“诊断必填”自行算；最好后端返回缺项列表，避免两边规则漂移 | P1 |

### 帮助与工单
| 项 | 说明 | 优先级 |
|---|---|---|
| 帮助中心内容 | 当前无接口；设计阶段用静态问答 | P2 |
| 工单附件 | 当前无；先不做上传 | P2 |

## 三、需要核对的字段（设计里的假设）
| 设计假设 | 位置 | 核对点 |
|---|---|---|
| 每个样本有 `rank`、`total`、一句回答摘要 | `diag.ts` 的 `Sample` | 接口是否返回“回答里出现的品牌列表”？目前 `answerList()` 的其他品牌是虚构的 |
| 品牌印象：优点/短板标签与原文引用、同场品牌出现次数 | `Impression.tsx` | 是否有对应接口；若没有，该 tab 需要降级或由后端新增 |
| “AI 推荐指数”0–5 与星级 | `Home` / `Report` | 以后端 `recommendationIndex` 为准，前端只展示；名称保持不变（用户决定） |
| 主动提及率（“找品牌”类问题命中率） | `METRICS.findRate` | 与后端定义对齐 |
| 平台顺序 | `PLATFORM_NAMES` | 接口按平台 key 返回；前端用固定顺序渲染，不依赖返回顺序 |

## 四、需要在接入时重构的前端部分
| 项 | 现状 | 接入时 |
|---|---|---|
| 数据来源 | 各页面从 `diag.ts` / `shared.tsx` 读样本 | 换成 Query hooks，保留 `SAMPLES` 作为 Storybook/空态样例 |
| 账户 | `Design.tsx` 的 `balance` | 全局账户 query + 乐观以外的写入流程 |
| 路由 | `useState<Page>` | Next.js 路由；`go(page, params)` 映射到路径与查询参数 |
| 品牌状态 | 第 1 阶段的 `brandState` 选择器读本地状态 | 改读后端聚合（或前端由多个接口派生），状态名保持不变 |

## 五、接入阶段的讨论清单（暂不展开）
- 订单是否需要“申请取消”（目前无，设计上不放入口，只做说明）。
- 通知是否需要已读同步到服务端。
- 诊断是否允许用户对评测问题“提出换一个”的轻量入口。

## 第二轮新增核对项
- 媒体库：`type / badges[] / etaDays / unitPoints / sample{title,excerpt} / logoUrl`；真实 Logo 的版权由运营提供。
- 品牌资料：完整度清单、地址（高德）校验结果、价格范围与单位的存储结构；保存后是否生成新“资料版本”。
- 文章：生成时引用了哪些资料项（可选：对应段落区间）。
- 诊断进度：能否返回每条回答的阶段（采样/解析/完成）；若只有完成数，前端以完成数为准并保持“只增不减、封顶 96%”。

## 第三轮新增假设（详见 15-round3.md）

| 模块 | 假设 | 优先级 |
|---|---|---|
| 品牌 | 品牌列表、切换、新建；切换后资料、诊断、文章、订单按品牌隔离 | P0 |
| 通知 | 站内通知列表、已读、全部已读；仅站内，无短信/邮件 | P1 |
| 工单 | 创建（分类、描述、关联订单）、列表、回复、状态（待处理/处理中/已解决）；FAQ 可由后台配置 | P1 |
| 媒体 | 详情字段：分类、标识、介绍、读者、收录要求、限制、样例、预计上线天数区间 `[min,max]` | P0 |
| 订单 | 详情：每家媒体一行（mediaId、状态 live/review/queued/failed、上线时间）；失败项退积分；72 小时结算 | P0 |
| 支付 | 积分充值支持支付宝与微信（1 元 = 10 积分）；微信返回二维码/拉起参数与轮询结果 | P0 |
| 资料 | 品牌特点改为 `{name, detail, proof}`；价格为 10 元一档的区间或“面议”，不再有计价单位；地址为高德 POI（名称、行政区、完整地址） | P0 |
| 文章 | 风格参数：目的（多选）、语气、结构、篇幅、补充要求；正文以 HTML 存储（Tiptap 输出），另存纯文本供发布；确认后编辑回到草稿 | P0 |
| 媒体（第 6 轮） | 详情页需要 `fit`（适合发什么）与 `rules[]`（文章长度、是否可带外链、审核方式），当前由前端按类别示例；若按单个媒体配置，请在媒体接口中返回 | P1 |
