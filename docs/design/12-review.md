## 三、举一反三：现有设计的系统性问题

按“影响用户走完流程”的程度排序。每项标注计划处理的阶段。

### A. 流程是断开的（影响最大）
1. **没有统一的品牌状态**。首页、报告、运行页各自用样本数据，“下一步”靠写死（Home 里“建议下一步”徽标固定贴在发布卡上）。用户的真实位置应由一个状态派生：`资料完整度 → 诊断状态 → 文章状态 → 订单状态`。→ 第 1 阶段。
2. **所有 CTA 都回首页**（`Report` 的优化方向、`Running` 的“完善文章/查看订单”等都是 `go('home')`）。用户要求模块紧密衔接，评测→内容→发布要能一路点下去。→ 第 1 阶段。
3. **门槛处会把人赶出流程**。积分不足、资料不全时，应就地给出补救（抽屉里充值 / 抽屉里补资料），完成后回到原处继续，而不是跳走。→ 第 1、4 阶段。

### B. 数据口径不是单一来源
4. “AI 推荐指数 3.5”在 `Home.tsx:191`、`Report.tsx:85/87` 三处写死，而 `diag.ts` 的 `METRICS` 里没有它。应放进 `METRICS`（或后续的 API 类型）一处定义，页面只读。
5. Home 的“50+ 家媒体”、`ARTICLE`/`ORDERS` 在 `shared.tsx`，诊断数据在 `diag.ts`——应按领域拆成各自的数据文件，页面不再自带样本。
6. `answerList()` 里的“其他品牌”来自虚构的 `POOL`，真实接口是否提供回答里的品牌列表需要确认（见 13）。
7. 各页面各自维护 `balance`（`Design.tsx` 的 `useState(2800)`），后续扣费/充值/订单需要同一个账户状态。

### C. 状态覆盖不全
8. 每个页面只设计了“成功/进行中”。缺：空、加载、部分失败、样本不足、被门槛锁住。诊断的状态矩阵在 `11-diagnosis` 已写但未落成界面。→ 第 2 阶段补齐。
9. 失败文案三段式（发生了什么 · 影响 · 怎么办）只在文档里，界面里还没有一个统一的 `ErrorNotice`。

### D. 视觉与编码一致性
10. **橙色承担两个含义**：“你/排位”与“内容服务色”。已在 `02-tokens` 写明规则（诊断页内橙=你；内容页内橙=服务色；同屏不混用）。第 3 阶段做内容页时需严格遵守，并检查报告里“去写文章”类按钮用蓝色主按钮。
11. 同场品牌气泡里“你”是蓝色，违反“你永远是橙色”（`Impression.tsx` 的 `Peers`，`fill-brand`）。第 1 阶段小修。
12. Points 页的大圆环装饰透过充值卡片显示，干扰表单阅读；报告 Hero 左下留白过大。第 1 阶段目视小修。
13. 充值页同时展示支付宝与另一种支付方式，而后端目前只有支付宝 PC 可用。只展示可用方式，避免承诺做不到的事。→ 第 4 阶段处理积分时一并改。

### E. 可达性与交互细节
14. 所有可点元素需要 `aria-label`/键盘可达（目前图标按钮基本有，列表行点击区域需复查）。
15. `Home` 的“查看全部”、`Report` 的“去更新品牌资料”是无动作按钮，随对应模块落地时接通。
16. 动效时长散落在各文件（0.2/0.22/0.25/0.35/0.6/1…）。沿用 `05-motion` 的取值，新增页面不得再引入新的时长，已有的在复查时归并。

### F. 技术债
17. 页面切换仍是 `useState<Page>`，没有路由。设计工作台阶段可接受；第 1 阶段在引入跨模块链接时先登记路由表（页面 → 路径 → 入参），生产再落地。
18. `src/imports/` 里 6MB 的原始线框 HTML 与截图仅作参考，不参与构建；如不再需要可以归档到仓库外。
19. `plans/` 下是历史计划文件，仅作归档。

## 四、关键设计思考（供第 1 阶段落地）

### 1. 品牌状态机（“下一步”的唯一来源）
| 状态 | 判定 | 首页主推 | 门槛提示 |
|---|---|---|---|
| 无品牌 | 没有任何品牌 | 创建第一个品牌（引导） | — |
| 资料未完成 | 诊断必填项未齐 | 补全资料（显示缺哪几项） | 诊断被锁，说明缺项并就地补 |
| 可诊断 | 资料齐、没有当前版本的诊断 | 开始诊断（显示消耗积分） | 积分不足 → 抽屉内充值 |
| 诊断中 | 评测进行 | 查看进度 | — |
| 诊断失败/需重试 | 样本不足 | 重试（不扣额度） | 说明是平台采样问题 |
| 已出报告 | 有报告、无确认文章 | 写第一篇文章（带入优化方向） | 文章信息不全 → 就地补 |
| 文章草稿 | 草稿未确认 | 确认文章 | — |
| 可发布 | 有确认文章 | 去发布 | 积分不足 → 抽屉内充值 |
| 发布中/已完成 | 有订单 | 看结果 / 复测 | — |

“资料版本变化后需要重新诊断”：资料改动后，旧报告打上“基于旧资料”标记，并把主推切回“可诊断”。

### 2. 评测→内容→发布的衔接
- 报告每条优化方向带 `{问题, 平台, 缺失点}`，点击“去写文章”进入内容页并**预填写作方向**，页首显示“来自诊断：Q3 · 腾讯元宝”。
- 文章确认后，成功态上直接给“去发布这篇”，进入发布页时**已选中该文章**。
- 订单有结果后，在订单详情给“复测一次”，形成 诊断→内容→发布→复测 的闭环。
- 链接统一走一个 `go(page, params)`，页面不自己拼状态。

### 3. 首个品牌引导
登录后若没有品牌：单屏“创建第一个品牌”（品牌名 + 行业），完成后直接进入品牌资料分步表单（同一个组件，`mode="onboarding"` 仅多一条欢迎语），完成必填项后落到“开始诊断”。不另做一套流程。

### 4. 就地补救（门槛的统一模式）
`GateNotice` 已有“原因 + 补救入口”。补救入口统一打开右侧 Sheet（充值 / 补资料），完成后关闭 Sheet、门槛自动解除、用户停在原页面。

## 五、阶段计划

每个阶段结束都先目视验证（Chromium 截图 + 控制台无报错），再向用户汇报，确认后进入下一阶段。每个新模块动手前，先联网调研 2–3 个优秀案例并把借鉴点写进 `09-roadmap` 的“组件选型原则”。

| 阶段 | 内容 | 完成标准 |
|---|---|---|
| 0 ✅ | 导入、环境、统一与清理、记录 | 4 页可渲染，控制台无运行时报错，文档与代码一致 |
| 1 ✅ | 状态派生与跨模块链接：`brandState` 选择器、`go(page, params)`、首页主推由状态驱动、报告/运行页 CTA 直达；就地补救 Sheet 骨架；第三节 11、12 的小修；指数与指标收口到单一来源 | 从报告一路点到“去发布”不经过首页；切换演示状态时首页主推随之变化 |
| 2 | 首个品牌引导 + 品牌资料分步表单（#4）；诊断状态矩阵（空 / 部分失败 / 样本不足 / 锁定）；TopBar 品牌切换器 | 缺项时诊断被锁且能就地补；每个状态都有界面 |
| 3 ✅（主线） | 品牌内容状态机（#5）：文章信息 → 草稿 → 确认；编辑已确认文章回退草稿的提示；重新生成的替换警告；失败态 | 状态机每一步都可走通，橙色规则不冲突 |
| 4 ✅（主线） | 媒体发布（#6）：套餐/精准、媒体筛选、确认 Sheet、积分不足就地充值；充值页只留可用支付方式 | 从确认文章到提交订单一路可走通 |
| 5 | 订单详情（#7）、通知中心、帮助与工单、移动端底部 Tab（#8） | 铃铛、品牌资料等入口全部有去处 |

## 五·补、已落地的第 1/3/4 阶段说明
- `flow.tsx`：`FlowProvider` 持有页面、`go(page, params)`、余额、诊断/文章/订单，`state` 由它们派生（ready → report → draft → publishable → published）。评审页顶部的“品牌状态”条可直接切换，首页主推随之变化。
- 报告“补全服务范围”带 `{Q3, 腾讯元宝, 服务范围}` 进内容页；确认文章后“去发布这篇”进发布页并已选中；下单后“查看订单”回首页并展开新订单；订单区有“复测一次”。
- `ui.tsx`：`Sheet`、`GateNotice`、`RechargeSheet`。积分不足时在发布页底部就地充值，成功后留在原页。
- 内容页：写作信息 → 检查草稿（实时“内容覆盖”清单，诊断缺口标“诊断重点”）→ 已确认。重新生成与编辑已确认文章都有就地确认浮层；含“模拟失败”演示。
- 发布页：套餐/精准；确认订单抽屉含条款勾选、“不可取消、72 小时结算”说明。
- 小修：Peers 中“你”改橙；充值卡不透明；充值页只留支付宝；指数 `METRICS.index` 单一来源。
- 未做（留给后续阶段）：品牌资料表单、首个品牌引导、诊断状态矩阵、订单详情页、通知中心。
- 套餐档位、媒体清单与价格为占位数据，接入时以后端报价为准。
